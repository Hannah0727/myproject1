## Context

`EventListDataView` 會依搜尋字串與頁碼組裝公開 JSON 列表；前端每次載入、搜尋、分頁或返回瀏覽紀錄時都會呼叫此端點。專案的 `default` cache 已使用 Redis，統一有效期為 60 秒。`Event` 具有依建立時間倒序的預設排序，因此新活動會改變未篩選列表以及可能符合名稱搜尋的所有結果頁。

快取需沿用 Django cache API，而非直接操作 Redis 客戶端。活動不只可從 `EventCreateView` 建立，也可能由 Django Admin、管理指令或未來程式入口建立，因此失效機制不能綁定單一 view。

## Goals / Non-Goals

**Goals:**

- 重複的相同活動列表 API 請求在有效期內重用伺服器端快取。
- 新增活動的資料庫交易成功後，讓後續所有活動列表 API 變體取得新版本資料。
- 維持既有 API 回應格式、搜尋與分頁行為。

**Non-Goals:**

- 不快取活動詳情、活動建立表單或前端 DOM。
- 不為活動更新、刪除、標籤或使用者名稱異動加入失效邏輯。
- 不修改 Redis 連線、全域有效期或新增快取後端。

## Decisions

### 以正規化請求參數與列表版本組成快取鍵

列表資料的快取鍵由固定命名空間、目前列表版本、去除首尾空白的搜尋字串與最終採用的頁碼組成。搜尋字串與頁碼不同即為不同快取項目；同一組輸入會讀取同一項目。回應仍沿用 `items`、`pagination` 與 `query` 的既有 JSON 形狀。

使用列表版本可在不枚舉未知搜尋字串與頁碼組合的情況下，整體淘汰舊資料。相較於 Redis pattern delete，此做法只使用 Django cache API，且不會在請求路徑執行大量鍵掃描。

替代方案：使用 `cache_page` 並在建立活動時刪除所有可能 URL 快取鍵。捨棄，因為快取鍵會受查詢參數和 HTTP 設定影響，無法可靠地涵蓋所有變體。

### 在 Event 建立的交易提交後推進列表版本

以 `Event` 的 `post_save` 建立事件作為失效入口，僅在 `created=True` 時註冊 `transaction.on_commit` 回呼以推進列表版本。Django app 啟動時載入該訊號處理器。交易成功前不改變版本；交易回滾時既有快取保持有效。

替代方案：在 `EventCreateView.post` 建立後直接刪除快取。捨棄，因為會漏掉 Admin 或其他程式化建立入口，也可能在交易回滾時過早失效。

### 快取內容包含完整成功 JSON 回應

API 先依現有規則將請求正規化和決定實際頁碼，再快取完整成功回應；後續命中快取時直接回傳相同資料。快取未命中、Redis 暫時不可用或快取寫入失敗時，API 仍依原有查詢與 JSON 回應流程完成請求，不把快取故障暴露給瀏覽器。

替代方案：只快取 `Event` queryset 或個別欄位。捨棄，因為快取 ORM 物件會增加序列化與失效複雜度，且仍需要每次重建分頁資料。

## Implementation Contract

**行為與資料形狀：** `GET /events/data/` 對相同的正規化 `q` 與最終頁碼，在活動列表版本未改變且既有 60 秒有效期內，回傳已快取的完整 JSON。JSON 的 `items`、`pagination`、`query` 欄位及其值規則不變。首次計算或快取未命中時，端點查詢資料、生成回應並快取它。

**失效：** 新 `Event` 的建立交易提交後，活動列表版本必須改變。版本改變後，無論是未篩選、名稱搜尋、第一頁或其他頁碼，下一個 API 請求都不得讀取建立前版本的快取資料。透過任何 ORM 建立入口新增的 `Event` 都適用。

**失敗與邊界：** 無效或超出範圍的頁碼仍遵循既有正規化結果；此最終頁碼用於快取。快取讀寫或版本操作失敗時，端點必須照原有方式成功產生 JSON，而非回傳快取專屬錯誤。僅建立活動觸發失效；更新與刪除不在本次範圍。

**驗收：** Django 測試須證明相同 API 請求不重複執行列表查詢、建立並提交新活動後的下一個請求包含新資料，且先前已快取的搜尋／分頁變體不再被採用。既有列表 API 測試必須持續通過。

**範圍：** 本變更限於 `apps.chillme` 的列表 JSON API 與 `Event` 建立失效鉤子；不改變前端 JavaScript、網址契約、資料模型欄位或 Redis 基礎設施。

## Risks / Trade-offs

- [版本鍵遺失或過期會使失效程式無法遞增] → 在讀取時建立可用的初始版本，並以測試涵蓋首次請求與首次建立事件。
- [快取服務暫時不可用] → 將快取視為最佳化；保留原本資料庫查詢與 JSON 回應路徑。
- [同時建立活動與讀取列表] → 使用交易提交後才切換版本；交易提交前的讀者可得到舊的一致快取，提交後的新請求使用新版本。
