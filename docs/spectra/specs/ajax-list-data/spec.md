## Requirements

### Requirement: Data lists load through an asynchronous endpoint

Pages that present a collection of persisted application records SHALL render the page shell first and obtain the list items from a same-origin asynchronous data endpoint. The endpoint SHALL return only the data needed to render the list and its pagination metadata. Static lists and one-off form option lists are outside this requirement.

#### Example: A visitor opens a data-list page

- **GIVEN** a visitor opens a page containing a persisted-record list
- **WHEN** the page becomes ready
- **THEN** the browser requests the list data asynchronously
- **AND** the returned items are rendered into the list area without a full page reload

---
### Requirement: Data lists provide bounded pagination

Every asynchronous data-list endpoint SHALL accept a page selector and return the current page, total page count, and whether adjacent pages are available. The list UI SHALL provide usable previous and next controls and preserve active filters when the page changes.

#### Example: A visitor moves to another search-result page

- **GIVEN** a visitor has searched a data list
- **WHEN** the visitor chooses the next page
- **THEN** the request includes the existing filters and the selected page
- **AND** the UI renders that page's records and pagination state

### Requirement: Data lists communicate loading, empty, and error states

The list area SHALL visibly distinguish loading, a successful empty result, and a failed request. During loading, pagination controls SHALL prevent duplicate page-change requests. A failed request SHALL offer a retry action; if earlier data is visible, it SHALL remain visible until a later request succeeds.

- **GIVEN** no list data has been rendered yet
- **WHEN** the asynchronous request fails
- **THEN** the UI displays an understandable error state and a retry action
- **AND** it does not present the failure as an empty result

#### Example: A later page request fails

- **GIVEN** the list has rendered a successful page of data
- **WHEN** a request for a different page fails
- **THEN** the existing records remain visible
- **AND** the UI displays an error and a retry action

---
### Requirement: Asynchronous persisted-record lists

The system SHALL render the page shell for a persisted-record list and SHALL obtain the list records from a same-origin asynchronous endpoint. The endpoint SHALL return the item data required by the list and pagination metadata. Static lists and one-off form option lists are outside this requirement.

- **THEN** the browser requests the event records from the asynchronous endpoint

#### Scenario: Visitor moves through filtered results

- **THEN** the request includes the active filter and selected page
- **AND** the UI renders the returned records and adjacent-page availability

### Requirement: Observable list request states

The list UI SHALL distinguish loading, successful empty results, and failed requests. While a request is pending, the UI SHALL prevent duplicate pagination requests. A failed initial request SHALL show an error and retry action. If a later request fails after records have been rendered, the UI SHALL retain those records and show an error with a retry action.

#### Scenario: Initial request fails

- **WHEN** the first asynchronous list request fails
- **THEN** the UI displays an error state and retry action
- **AND** it does not display the failure as an empty result

#### Scenario: Later page request fails

- **GIVEN** the UI has rendered records from a successful request
- **WHEN** a request for another page fails
- **THEN** the existing records remain visible
- **AND** the UI displays an error and retry action

### Requirement: Asynchronous event-list data is cached and invalidated after event creation

The system SHALL cache successful event-list asynchronous endpoint responses using the normalized search query, resolved page, and current event-list cache version. The system SHALL retain the existing JSON response structure and configured cache lifetime. After a new event is created and its database transaction commits, the system SHALL advance the event-list cache version so every later event-list request bypasses responses cached before that creation, regardless of search query or page. Cache service failures MUST NOT prevent the endpoint from returning a freshly generated successful response.

#### Scenario: A repeated request reuses an event-list response

- **WHEN** a visitor requests the event-list asynchronous endpoint twice with the same normalized search query and resolved page before the cache expires or the cache version changes
- **THEN** the second response SHALL reuse the cached successful response and preserve the existing JSON structure

#### Scenario: A new event invalidates every cached list variant

- **WHEN** a new event is created through any ORM entry point and its database transaction commits
- **THEN** the next event-list asynchronous request for any search query or page SHALL not use a response cached before that event was created

#### Scenario: A creation transaction is rolled back

- **WHEN** creation of a new event is rolled back before the database transaction commits
- **THEN** the event-list cache version SHALL remain unchanged

#### Scenario: The cache service is unavailable

- **WHEN** the event-list asynchronous endpoint cannot read or write its cache
- **THEN** the endpoint SHALL generate and return a successful response using its existing list-query behavior
